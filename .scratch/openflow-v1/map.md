# OpenFlow V1 — Wayfinder Map

## Destination

A locked, executable plan for shipping **OpenFlow V1**: an open-source Android voice-dictation app (floating bubble, not an IME) with a provider-neutral Adaptive Dictation Router, local-first privacy, and a passing acceptance gate — with CI, a release APK, and a working Pages site. The site is the **project page**, settled in ticket 26: it explains the product and links to these documents, it does not re-render them.

The gate has **two bars**, settled in ticket 28: a prerelease tag requires 14 scenarios green on one device class, `v1.0.0` requires all 14 on all three. "Shipped" still means all three classes — the hardware gap is reported, never redefined away.

## Notes

- Domain: Android voice dictation; NOT an IME; bubble-driven.
- Every ticket should consult `GLOSSARY.md` for vocabulary.
- Standing preferences settled during charting:
  - Name: **OpenFlow**; Apache-2.0; three Gradle modules (`app/`, `core/`, `providers/`) but layout must be easily expandable (documented seams/extension points, no empty modules).
  - Provider-neutral: no `if provider == X` in app code; capabilities-driven.
  - First real provider: sherpa-onnx; FakeProvider for tests; whisper.cpp/cloud providers are future adapters.
  - V1 TranscriptRefiner is deterministic only (no local LLM).
  - History storage: Room once complexity warrants; keep simple at first.
  - Audio deleted after successful processing by default; never retain by default.
  - **Design language: brutalist.** Zero radius, no shadows, flat ground, one accent, hairline rules, 2px structural borders, sentence case, mono for machine-voice copy (set limits in mono against capabilities in the UI face). Accent: electric violet, a separate value per theme, verified WCAG AA for every text role.
  - **Typography is now decided, and it was not before.** Archivo (variable, weight 100–900 **and width 62–125%**) for everything, set EXTENDED at weight 800 for display against normal-width body — the width axis is the site's typographic idea, not a scale. JetBrains Mono for machine voice only. Both self-hosted as committed woff2, latin subset, ~127 KB total. Ticket 19's prototype had picked these faces but no document ever recorded the choice, so the app and the site would have drifted; the app should inherit this rather than re-decide it.
  - **The landing page's honesty rule is the one idea worth stealing.** Every claim is set against what it cannot do, the limit half in mono beside the promise half in the UI face — generalised from ticket 19's permission screen, and now the organising device of the whole site. A promise nobody has bounded is not a promise.
  - **The site carries no invented numbers.** There is no benchmark figure on it because ticket 25 has not reported one. When real RTF numbers exist they go on the page and nowhere else.
  - **Motion has one rule: structure draws itself, and nothing else moves on its own.** No scroll-triggered fades-and-slides — that is the most recognisable generated-page tell. The page-load entrance is the single choreographed moment; everything after it is a rule scaling out from an edge, a marker growing down, or a wire drawing along its own path. All of it is gated on a `js` class set synchronously in `<head>`, so **nothing on the site is invisible without JavaScript** — a hero that `opacity: 0` by default is a blank page the moment a script fails.
  - **`position: sticky` carries the story, not scroll-jacking.** On a wide screen the phone is pinned while the six claims scroll past it, and its caption names whichever claim you are reading, so you read each limit while looking at the thing it is about. No scroll hijacking, no parallax on everything, no progress bar: motion that answers a pointer or a scroll position, never motion that takes the wheel.
  - **Nothing may be hidden by default.** The first build of the entrance animation set `opacity: 0` as a base state, which meant a blocked or failed script left the entire hero blank. Start states live behind `.js`, and animations use `fill-mode: backwards` so an animation that never runs leaves its element visible rather than absent.
  - **Mobile gets DOM order, desktop gets grid areas.** The three top-level blocks are siblings — promise, device, qualifications — so the narrow layout reads in the right order without `order` hacks, and the pinned arrangement is a `grid-template-areas` statement rather than a rearrangement.
  - **`pages.yml` needed two repairs, not one.** It was missing `actions/configure-pages`, which is what enables Pages and authenticates the deploy — without it `deploy-pages` fails with a 404 and the site is built and never published. Pages was also not enabled on the repository at all. Both fixed in ticket 26; the probe that skipped the deploy when `website/` was absent is gone, because a conditional that can never be false is a stale promise.
  - **The Pages site is a project site, not a user site**, so it is served from a subpath. Every internal link, stylesheet and font URL in it is relative, which is what makes that a non-issue — worth keeping true if a custom domain is added later.
  - **Granted/permitted state is shown by the row's own perimeter drawing clockwise** (conic-gradient mask), never a bar bolted to the side of the row.
  - Permissions are requested **contextually, not at first launch** (settled in ticket 03) — so any onboarding flow must justify its order against this, not against a generic wizard.
  - **CI is green from the first commit.** Workflows whose steps need files that do not exist yet probe for them and skip rather than failing, so a required check is usable while the code is still being written. Settled in ticket 23; this is the standing rule for any workflow added later.
  - **No stale documents.** A document that points at a file that does not exist, or promises one nobody wrote, is a bug — a reader cannot tell it from a correct one. `docs-check` enforces it; see ticket 23.
  - **No bots in the contributor list — enforced, not just intended** (settled in ticket 23, which put `attribution.yml` behind the rule AGENTS.md already stated). No `Co-authored-by` or `Signed-off-by` trailer may name a bot, an automation account, or an AI assistant; `main` is owner-authored only; automation never writes to a branch here. Human co-authors are fine, including the trailers GitHub appends by itself when squashing.
  - **`main` is branch-protected, and the gates only started working once ticket 23 was actually pushed** — until then `main` ran no CI whatsoever, so nothing below had been exercised. Live as of ticket 18: a PR is required, and `Lint, test, assemble`, `Documentation integrity`, and `Commit attribution` are required contexts (resolved by GitHub to Actions `app_id 15368`, so they are real checks, not free text). Linear history, no force-push, no deletion, conversation resolution required, admins included. **`required_approving_review_count` is deliberately 0** — this is a solo-maintained repo and one approval would deadlock the owner. Because `enforce_admins` is on, *nothing reaches `main` except a green PR, including the owner's own pushes.*
  - **A required status check must be able to report on every PR, and must be able to pass.** A `paths:` filter on a check that branch protection requires is a deadlock: GitHub blocks the PR forever waiting for a check that will never run. This is why `docs-check` is deliberately **unfiltered** — as originally written it only ran on `**/*.md` changes, so on a code-only PR it never reported and the gate was decorative. Any check added to the required list must run unconditionally on `pull_request`, and must be verified end-to-end on a real PR before it is required — verify the trigger *and* the outcome, not the trigger alone. Requiring a check nobody has ever seen pass is worse than not requiring it: it blocks every merge while looking configured.
  - **`GitHub <noreply@github.com>` is GitHub's merge machinery, not an automation account**, and must never be treated as a bot. It is the committer of every synthetic `pull_request` test-merge commit and of any web-UI squash. `check_attribution.py` now exempts it as committer only — exempting it as author, or exempting `[bot]` accounts, would gut the rule AGENTS.md states. See ticket 18, where requiring `attribution` without this made the repo unmergeable.
  - **A web-UI squash re-attributes the author email** to the account's public address (`mitunmanav933@gmail.com`), not the identity pinned in AGENTS.md. `attribution` still passes because `is_owner` matches on name, so R2 is one display-name change away from breaking. It is a GitHub account setting, not a repo one.
  - **The dependency graph is enabled** (`vulnerability-alerts` + `automated-security-fixes`), so `dependency-review` actually runs instead of failing with "not supported on this repository".
  - **Dependabot's landing path is settled: automation proposes, a human authors, a human merges** (ticket 29). The rule binds the landed commit's **attribution**, not the diff's provenance — so a bot's diff lands by being **re-authored locally**, and no GitHub-native merge can do it: squash-merge attributes the squash to the PR's *author* (which is why PRs #2/#3 landed as `Mitun Manav G Y`), and rebase-and-merge preserves the bot author. **A plain `git cherry-pick` does not work either — it preserves the original author**, producing exactly the commit the check exists to reject. The bot's own `Signed-off-by` is stripped and a non-authorship `Refs:` pointer added, because the manual route loses GitHub's free `(#7)` subject link and the audit trail would otherwise vanish. **`check_attribution.py` needs no change and gains no exemption.** No security-fix carve-out: `automated-security-fixes` arrives as bot PRs too, but ticket 28's waiver precedent deliberately does not transfer — a skipped gate is recoverable, a bot-authored commit in history is not. Reasoned in `docs/adr/0009-automated-dependency-landing-path.md`. **Still unimplemented**: ticket 39 (the procedure), with ticket 38 narrowing the dependency groups first so the procedure's first outing is not eight breaking CI bumps at once. A red Dependabot PR is still not a malfunction.
  - **`release.yml`'s `verify` job and `build` job are at different maturities, and the gap is now ticket 35.** `verify` only reads the four secret *names* (exercised in ticket 23); `build` decodes the keystore and writes a `signing.properties` that **no build file reads** — `app/build.gradle.kts` has no `signingConfigs` block, so the release build is unsigned and the workflow's own signature-verification step would fail. This was ticket 27's gap; 27 deliberately did not take it, so it is now ticket 35. Two things to carry there: `signing.properties` is **not** in `.gitignore` today, and a release run must fail loudly rather than fall back to the debug key.
  - **The project has one or two real Android devices, not three** (established in ticket 25). This is a hardware fact, not a preference, and it reaches further than the model choice: the destination's three-device acceptance gate cannot be run as written, and `model-selection.md`'s threshold — "RTF ≤ 0.3 on the weakest tier" — has no weakest tier to be measured against. Two consequences to hold onto: the V1 model default is **unconfirmable before shipment**, and the acceptance gate is **aspirational until hardware exists** (ticket 28). Do not let either be quietly redefined to fit what is on hand.
  - **Measure models with the prebuilt sherpa-onnx demo APKs first, the provider harness second.** The demos cover the whole `model-selection.md` matrix — including an APK carrying the exact V1 default, `sherpa-onnx-streaming-zipformer-en-20M-2023-02-17` — run offline, on `arm64-v8a`/`armeabi-v7a`/`x86_64`, with **zero code**. That matters because the alternative method named in `model-selection.md` ("script via the same Kotlin API the provider will use") is blocked on ticket 27, and a decision sitting under the acceptance gate should not wait on a build that does not exist. The demo numbers are directional; the harness numbers (ticket 30) are the shipping ones, and both go in the same results document as separate sections rather than overwriting each other.
  - **There is now an Android build, and it is green.** Ticket 27 landed a Gradle 8.13 / AGP 8.13.0 / Kotlin 2.0.21 project (`compileSdk`/`targetSdk` 36, `minSdk` 26) with the wrapper committed; `ci` no longer skips and its `paths:` probe is now load-bearing on a file that exists. `./gradlew lint test assembleDebug` passes from clean. **What it proves is narrower than a green check suggests: it assembles and it proves the sherpa-onnx AAR is consumable, and it runs zero tests** — there is still no application code, so do not let a green gate imply behaviour is covered. Versions live in `gradle/libs.versions.toml`; reasoning in `docs/adr/0007-build-toolchain-and-sdk-levels.md`.
  - **CI runs JDK 17, deliberately, and the workflows were changed to match.** They were written for temurin 21; ticket 27 moved `ci`, `android-test` and `release` down to 17 so the build runs on the same JDK on the development machine as it does in CI. Java 17 is targeted through `compileOptions`/`kotlin { compilerOptions }` with **no `jvmToolchain` block**, so Gradle runs on whatever JDK starts it. A toolchain block plus a JDK-resolver plugin remains available as a tightening, and needs a fresh ADR when taken.
  - **The sherpa-onnx dependency is heavier than expected and free of NDK.** The AAR is **50,129,134 bytes** for four ABIs, available **only via JitPack** (not on Maven Central), and carries **no transitive dependencies** — the library declares androidx as `implementation`, so nothing androidx is re-exported. JitPack *mirrors* sherpa-onnx's own release artifact rather than compiling it, which is why no NDK is needed. **Pin the coordinate to a tag: upstream's JitPack config hardcodes the version it mirrors**, so `master` can resolve to an AAR that contradicts the coordinate. `isMinifyEnabled = false` because that AAR ships an **empty** `consumer-rules.pro` while its JNI layer resolves classes by name — ticket 33.
  - **`app-debug.apk` is 129 MB** (four ABIs, nothing stripped). CI uploads it on every run. Release size, ABI splitting and any size ceiling are undecided — ticket 33.
- Acceptance gate for "shipped": three device classes (Pixel-like, Samsung-class, Xiaomi-class) × **fourteen** scenarios (settled in ticket 28) all start → record → transcribe → clean → insert → recover cleanly, at three runs per cell with two of three passing. **The protocol is `docs/quality/acceptance-gate.md`; the two bars and tag-driven enforcement are `docs/adr/0008-acceptance-gate-two-bars.md`. No run has been performed and coverage is `N/3` classes.**
- **The acceptance gate has two bars, and "shipped" is still the strict one** (ticket 28). Releasable = a prerelease tag `v0.y.z` with all 14 scenarios green on one class; Shipped = `v1.0.0` with all 14 on all three. The tag's own major version selects the bar, so a version number cannot disagree with the destination. Narrowing the gate to the hardware in hand would have silently rewritten the promise, and keeping one bar would have meant no release ever ships.
- **A gate that cannot be run is not a strict gate, it is an absent one** — and the cost of the two bars is a release cadence: a full pass is ~2–3 h per class, so prereleases are a few times a year, not weekly. A weekly `v0.1.0-alpha.1` would mean skipping the gate, which is the one thing the bar exists to prevent.
- **Tags bypass branch protection entirely.** The `main` gate from ticket 18 gates PRs and cannot gate a tag, so the acceptance gate's enforcement has to live inside `release.yml` before publish. Adding it to branch protection's required list would be decorative — the same failure the Notes already record for `docs-check`'s original filter. **Not implemented yet: ticket 36.**
- **A waiver, not a silent bypass.** `gate_waiver_reason` must be non-empty and lands in the release notes. Somebody will eventually need to rebuild a tag on hardware nobody has; hard-blocking that is a problem people solve by deleting the workflow.
- **The gate tests the pipeline, not the model.** No scenario is ever failed for transcription accuracy; WER belongs to the model-selection work. A gate slow enough to be skipped is a gate with no results.
- **The ten original scenarios were partly uncalibrated for this product**, which is the general lesson: two tested the network in a product that transcribes on-device, and one was unpassable on the English-only bundled default. Re-homed to download-behaviour and the bilingual tier. Any future scenario should be checked against "does this discriminate anything about OpenFlow?" before it earns a slot.
- **All ten were content scenarios — what you say, not what the app does under stress.** Four mechanism scenarios were added. Content-only gates read as thorough while testing nothing about the state machine and the inserter.
- **Device class is behavioural, not a brand list.** Three questions about OEM hostility to overlays and background microphones, plus OEM skin and Android version. The three classes are on the list *because* they differ there, so a brand-based definition cannot tell two comparable phones from two incomparable ones. This is also what makes a crowdsourced run comparable to an owner's.
- **Crowdsourcing is the sanctioned route to closing the coverage gap**, not a workaround: an open-source project treats a user on an unbought device class as missing coverage rather than an inconvenience.
- **Three runs per cell, two of three, all three recorded** — the same discipline ticket 25 uses for measurement, so the project holds one rule for measuring things. Flake stays visible as a property; a scenario green 2/3 forever is visibly shaky, and unlimited retries measure nothing.
- **The gate is the project's only manual collection process, so it obeys the app's rules.** A failure's artifact is transcript + router decision log + state trace — both already produced by ADR-0004 and ADR-0002. Never audio: this project deletes recordings after processing and has no telemetry, and a gate retaining them would be a second retention path in the one place nobody was looking. Runs are committed and crowdsourced runs are public, so the checklist tells testers to dictate text they wrote themselves.
- **The gate's machine-readable status is a fenced `json` block embedded in the human document, and it is the only thing CI parses.** One file, so coverage and prose cannot drift, and a reworded paragraph cannot move a gate. Empty is not a pass — it is absence of evidence, and it blocks both bars.

## Out of scope

- Meeting notetaker / always-on transcription product.
- Monetization, accounts, cloud sync.
- iOS / desktop / web clients.
- Automatic ML-based provider routing (V1 router is rules + measurement only).
