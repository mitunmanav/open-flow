# OpenFlow V1 — Wayfinder Map

## Destination

A locked, executable plan for shipping **OpenFlow V1**: an open-source Android voice-dictation app (floating bubble, not an IME) with a provider-neutral Adaptive Dictation Router, local-first privacy, and a passing acceptance gate — with CI, a release APK, and a working Pages site. The site is the **project page**, settled in ticket 26: it explains the product and links to these documents, it does not re-render them.

The gate has **two bars**, settled by [How the acceptance gate is run and recorded](issues/28-acceptance-gate-protocol.md): a prerelease tag requires every required scenario green on one device class; `v1.0.0` requires every required scenario on all three. The [acceptance-gate protocol](../../docs/quality/acceptance-gate.md) defines the required IDs. "Shipped" still means all three classes — the hardware gap is reported, never redefined away.

R8's entire reachable surface is 0.82%. The generalisable lesson, and the one to carry: **before asking whether to minify, find out what the APK is actually made of.** A ticket can be unblocked, correctly scoped, and still ask the wrong question — the fix is not to answer it as written but to measure the premise. This is the same move as ticket 32's "verify against the resolved artifact, not against prose", applied to our own build output instead of a vendor's docs.

Nothing in the build catches it — the failure would be a runtime `UnsatisfiedLinkError` or `NoClassDefFoundError` on a user's phone. Same defect family as `docs-check`'s original `paths:` filter and as requiring a check nobody has seen pass. Recorded here because the *fix* for it is a behavioural test in the gate, not a build flag.

Cross-referencing those symbols against the `FindClass`-style class-name strings in the same binary: **82 of 122 classes (67.2%) are addressed by name from native code** (22 via symbols, 62 via strings, 2 overlapping). A single `-keep class com.k2fsa.sherpa.onnx.** { *; }` covers them. **But `OfflineDiacritization`, `WaveWriter` and `tts/engine/TtsEngine` are named by the native layer and absent from `classes.jar` in `v1.13.8`** — unprotectable, because there is nothing there to keep. - **A privacy product can decline to secure itself, and the reason is other people's
  apps.** The bubble takes no `FLAG_SECURE`, because that flag suppresses capture for the
  display region our window touches — so the bubble would break *every other app's*
  screenshots while it was up. We cannot secure another app's window, so the only outcome
  available was making everyone else worse. The rule already in the repo supplied the
  principle: do not suppress or mislead the privacy indicator, so do not defeat capture
  either. The generalisable trap: `FLAG_SECURE` reads as the privacy-correct choice and is
  the opposite here, because the surface we own is the one thing we are not entitled to
  restrict.
- **A permission's scope is set by what you promised, not by what would make insertion more
  reliable.** The accessibility service observes `TYPE_VIEW_FOCUSED` +
  `TYPE_WINDOW_STATE_CHANGED` and **does not** watch the keyboard and **does not** poll,
  both of which every reference app does and both of which would have improved target
  capture. Watching the keyboard would put keyboard observation behind the permission users
  grant to write text into a field; polling is the "background automation"
  `permissions-policy.md` forbids. Both rejected against our own published promise rather
  than against a principle, which is what makes them hold under pressure.
- **A platform capability we hold but decline must be disclosed as ours, not the OS's.**
  `ACTION_SET_TEXT` needs a handle on the focused field, so the service *can* read that
  field's text. `privacy-policy.md` previously said "we do not read surrounding field text",
  which reads as a platform guarantee and is not — it is a code-level discipline. The
  sentence now says the capability exists and we decline it. Same shape as the site's
  promise/limit rule: a promise nobody has bounded is not a promise, and a limit the
  platform enforces for you is not your restraint.
- **Store the invariant, and the migration question disappears.** The bubble's position is
  an **Anchor** — an edge or corner plus a margin in dp — not a coordinate. That dissolves
  the question ticket 34 was chartered to ask ("does it remember a position set before
  rotation?"): there is nothing to remap, because the stored value means the same thing on
  every display. The cost is real and stated in the glossary rather than discovered: the
  bubble cannot rest at an arbitrary interior position, because an interior position has no
  meaning on the next device. The generalisable move — when a position or an identifier has
  to survive a change you cannot predict, ask what it *means* rather than what it *was*.
- **`POST_NOTIFICATIONS` is a categorically different ask from `RECORD_AUDIO`, and the
  difference is what justifies it.** We want the microphone because we want to listen. We
  want notifications because our own foreground service cannot exist visibly without them:
  with `targetSdk` 36 and no such permission the service still runs and the notification is
  suppressed, so the failure mode is an invisible microphone. Nothing is read, nothing is
  sent, and the channel carries the recording indicator and nothing else, ever. Two
  consequences: it is requested at first dictation rather than bundled into any other ask,
  and **denial does not block dictation**, because the bubble is the recording indicator
  anyway — which is rather the point of a bubble product.
- **A ticket's own premise can be stale in the ticket's direction too.** Ticket 34 framed
  the accessibility disclosure as "a Play-policy matter", but the map rules a Play release
  out of scope, so that half was moot. The disclosure was kept anyway, and the Play Console
  declaration and its demo video dropped — because the honesty rule is not a Play artifact.
  Check the ticket's framing against **Out of scope** before grilling it; a question built
  on a policy this effort does not adopt wastes a round.
- **How ticket 34 was decided, because it changes how the answer reads.** It is a
  `grilling` ticket, which is supposed to resolve through live exchange. It did not: the
  owner was asked how to proceed and answered *"decide it for me."* So its answer is **the
  agent's judgement carrying the owner's sign-off, not decisions the owner made**, and it
  says so on its own first line. Worth remembering as a category: a grilling ticket
  resolved this way is not a broken grilling ticket, but it is a different artefact and
  should not be read as though someone weighed the alternatives. The three decisions most
  worth a second look are the deliberate non-obvious ones in
  `docs/adr/0011-bubble-overlay-window.md`.
- Acceptance gate for "shipped": three device classes (Pixel-like, Samsung-class, Xiaomi-class) × **every required scenario** in the [acceptance-gate protocol](../../docs/quality/acceptance-gate.md) all start → record → transcribe → clean → insert → recover cleanly, at three runs per cell with two of three passing. **The protocol is `docs/quality/acceptance-gate.md`; the two bars and tag-driven enforcement are `docs/adr/0008-acceptance-gate-two-bars.md`. No run has been performed and coverage is `N/3` classes.**
- **The acceptance gate has two bars, and "shipped" is still the strict one** (ticket 28). Releasable = a prerelease tag `v0.y.z` with every required scenario green on one class; Shipped = `v1.0.0` with every required scenario on all three. The tag's own major version selects the bar, so a version number cannot disagree with the destination. Narrowing the gate to the hardware in hand would have silently rewritten the promise, and keeping one bar would have meant no release ever ships.
- **A gate that cannot be run is not a strict gate, it is an absent one** — and the cost of the two bars is a release cadence: a full pass is ~2–3 h per class, so prereleases are a few times a year, not weekly. A weekly `v0.1.0-alpha.1` would mean skipping the gate, which is the one thing the bar exists to prevent.
- **Tags bypass branch protection entirely.** The `main` gate from ticket 18 gates PRs and cannot gate a tag, so the acceptance gate's enforcement has to live inside `release.yml` before publish. Adding it to branch protection's required list would be decorative — the same failure the Notes already record for `docs-check`'s original filter. **Implemented in ticket 36**, as a `gate` job that `publish` depends on, and it is currently red.
- **A waiver, not a silent bypass.** `gate_waiver_reason` must be non-empty and lands in the release notes. Somebody will eventually need to rebuild a tag on hardware nobody has; hard-blocking that is a problem people solve by deleting the workflow.
- **The gate tests the pipeline, not the model.** No scenario is ever failed for transcription accuracy; WER belongs to the model-selection work. A gate slow enough to be skipped is a gate with no results.
- **The ten original scenarios were partly uncalibrated for this product**, which is the general lesson: two tested the network in a product that transcribes on-device, and one was unpassable on the English-only bundled default. Re-homed to download-behaviour and the bilingual tier. Any future scenario should be checked against "does this discriminate anything about OpenFlow?" before it earns a slot.
- **All ten were content scenarios — what you say, not what the app does under stress.** Four mechanism scenarios were added. Content-only gates read as thorough while testing nothing about the state machine and the inserter.
- **Device class is behavioural, not a brand list.** Three questions about OEM hostility to overlays and background microphones, plus OEM skin and Android version. The three classes are on the list *because* they differ there, so a brand-based definition cannot tell two comparable phones from two incomparable ones. Keyboard behavior is a separate G12 observation. **The answer-to-class rule is settled in [64](issues/64-device-class-assignment.md): the class is *derived* from a recorded Hostility Profile by counting hostile answers, so it is recomputable rather than assigned, and an incomplete profile yields no class at all.**
- **A rule nobody can recompute is the label version of an unfalsifiable claim, and the fix is a published function rather than a better sentence.** Ticket 64 found the two former examples deciding by *brand* in one case and *behaviour* in the other, contradicting both each other and the section's own "brand is recorded but is not decisive". Six distinct rejections had already reached this map from one family — `docs-check`'s original `paths:` filter, requiring a check nobody had seen pass, the latency guard's uncalibrated threshold, ticket 44's half-landed count, a keyframe-held resting style, a press that cross-faded through sub-AA contrast — and this is the first where the artefact is a *judgement* rather than a piece of automation. Same shape: a class label nothing recomputes cannot be wrong in a way anyone would see, and **the absence of a rule reads exactly like the presence of a considered one.** The general form worth keeping: when a record states a conclusion, record the observations it came from and make the conclusion derivable, so the checker compares against the thing it claims to test.
- **A classification input that cannot be read off a device has to be discovered by running, which is why all three axes became probes.** Only the overlay axis was answerable as a question; the background-microphone axis — whether a skin silently blocks a backgrounded recording — is not legible in any settings screen, exactly as insets behaviour was in ticket 59. Keeping two questions and converting one would have produced a record **mixing a tester's guess with a measurement**, which is worse than either, because the two look like the same kind of evidence on either side of the block. A third value (`unknown`) then has to exist, and every default is wrong in one direction or the other — non-hostile credits an unmeasured device, hostile narrows the gate silently — so the only correct move is to derive nothing and report the device unresolved.
- **What identifies a class is a device in a configuration, not a device.** The same move that made the Bubble an `Anchor` rather than a coordinate: ask what the value *means* rather than what it *was*, and the rotation question dissolved. Here it dissolves "does changing a setting reassign it" — obviously it can, so the configuration is recorded, re-probing is required after any change that can move an answer, and **a changed class invalidates that device's earlier cells**, because results bind to the conditions that produced them exactly as they already bind to APK identity. The tempting alternative, a defaults-only purity rule, died on ticket 42's reasoning: it would exclude **precisely the handsets most likely to volunteer a run**, which is the route the map already depends on to close `N/3`. A gate that refuses honest devices gets the ones nobody volunteers.
- **Crowdsourcing is the sanctioned route to closing the coverage gap**, not a workaround: an open-source project treats a user on an unbought device class as missing coverage rather than an inconvenience.
- **Three runs per cell, two of three, all three recorded** — the same discipline ticket 25 uses for measurement, so the project holds one rule for measuring things. Flake stays visible as a property; a scenario green 2/3 forever is visibly shaky, and unlimited retries measure nothing.
- **The gate is the project's only manual collection process, so it obeys the app's rules.** A failure's artifact is transcript + router decision log + state trace — both already produced by ADR-0004 and ADR-0002. Never audio: this project deletes recordings after processing and has no telemetry, and a gate retaining them would be a second retention path in the one place nobody was looking. Runs are committed and crowdsourced runs are public, so the checklist tells testers to dictate text they wrote themselves.
- **The gate's machine-readable status is a fenced `json` block embedded in the human document, and it is the only input the release checker parses.** One file, so coverage and prose cannot drift, and a reworded paragraph cannot move a gate. Empty is not a pass — it is absence of evidence, and it blocks both bars.
- **The release build's inputs had never been read by anyone, and the first look found a second defect in the same file.** `versionCode = 1` / `versionName = "0.1.0"` are hardcoded and `release.yml` passes no version, so **the tag and the artifact's version are independent** — tagging `v0.2.0` publishes an artifact claiming `0.1.0`, and two distinct releases at `versionCode 1` fail to distinguish release identity (equal codes do not inherently prevent reinstalling; Android rejects lower codes). Not a one-liner: `versionCode` must strictly increase, a `workflow_dispatch` rebuild of a tag must not move it (ADR-0008 records gate results against a `version_code`, so a rebuild that changes it makes an existing Gate Status entry unverifiable), and `v1.0.0` is a gate bar selected from the tag's major version — so the artifact's own metadata can contradict the bar it shipped under. **50** owns it. The generalisable move: **ticket 35 was chartered to wire signing, and wiring it is what put a human eye on the only other inputs a release has.** A ticket about one property is the cheapest possible audit of the file it lives in. **Now fixed, by ticket 36:** `-Popenflow.releaseTag` derives both fields from the tag and `requireReleaseVersion` refuses a release build without one, *including CI's unsigned size probe* — permitting an unsigned artifact and saying which version it is are separate permissions, and ticket 50's implementation was handed to "the build and publishing workflow" with no owner until 36, which could not be finished without it.
- **The wire order in a workflow is a decision, and nothing checks it.** `publish: needs: [select, gate]` is the only thing standing between a red gate and a published Release, and the first draft of ticket 36's workflow had `publish` depending on `select` alone — which would have published on a failed gate, silently, in a file that looked entirely correct. Both jobs existed, both held real logic, the gate genuinely failed on the current record, and the release would still have shipped. Same family as requiring a check nobody has seen pass, and the closest this map has come to one: **a gate that is provably red and provably does not gate.** It is a YAML dependency edge, so no unit test in this repository can catch it and the only instrument that can is a real tag — which is why "the gate has never gated a release" is now a stated fact in both the protocol and ADR-0008 rather than an omission. The general form: **a check is not the enforcement, the position of the check is**, and a position is the part a test suite is worst at seeing.
- **A hand-filled schema's worked example is a copy-paste source, so its version number is load-bearing.** The populated block in the protocol's `### The shape of a populated block` carried `gate_version` 5 while the live record and ADR-0008 both said 6. Nobody typed a wrong value: ticket 48 wrote the shape, ticket 64 bumped the live block and the prose, and the example fence was not part of either diff. The consequence is worse than a stale document, because a tester fills a block **by hand from that example** — there is no generator, by three separate decisions — so the documented route to a valid record produced a record `check_gate.py` refuses outright. Sixth instance of this map's "an amendment touching a machine-read format is a change to its contract" family, and the first where the drifted copy is consumed by a **person** rather than a parser, which is why no amount of parser hardening would have caught it. The generalisable move: when a document is the input to a manual process, its examples are test fixtures, and the assertion worth making is that the example is *acceptable to the consumer*.
- **A merge button reads the pull request's author, not the commit's, so re-authoring the
  commit does not make the bot's pull request mergeable.** This was the decision ticket 39
  found and the ticket did not contain. ADR-0009 established that no GitHub-native merge can
  land a bot's diff and that the route is a local owner-authored commit; it stopped one step
  short. Force the re-authored commit onto Dependabot's branch and squash-merge *its* pull
  request and you still land `dependabot[bot]`, because the squash takes the author from the
  pull request. So the landing route is **your own branch, your own pull request, close the
  bot's** — which is what makes ADR-0009's `Refs:` pointer load-bearing rather than tidy: the
  free `(#n)` link came from the pull request being merged, and once the path is manual that
  pointer is the only surviving link to the bot's proposal. The general shape: **a gate on
  landed metadata can be satisfied by a commit while the platform's own attribution path
  still routes around it**, so "the commit is correct" is not the same claim as "this will
  merge".
- **A tool whose purpose is to make a rule passable earns its keep by refusing, not by
  succeeding.** The script ticket 39 built has six refusals and one happy path, and the
  refusals are the design: it will not re-author anything that is not automation-authored
  (otherwise it launders a collaborator's commit into the owner's name — R2 inverted), will
  not run under a non-owner identity, will not reset an existing branch, and has no
  `--force`/`--skip` flag at all. The ticket warned it "must not gain the owner a shortcut";
  the answer was not to add warnings but to make the tool narrower than the rule it
  enforces. Worth reaching for whenever a repo hands someone a script to satisfy a gate.
- **A guard that blocks on what it says it does not care about reads as a bug in the tool.**
  The dirty-tree check originally used bare `git status --porcelain` and so refused on
  untracked files — including the script's own `__pycache__`, which it created by importing
  its sibling module. Two defects with one cause: the guard's stated reason (untracked files
  cannot reach the commit) did not match what it tested, and the tool littered the directory
  it lived in. Fixed on both sides — `--untracked-files=no`, and `sys.dont_write_bytecode`
  before the import. The reusable move: **when a check fires on something obviously harmless,
  suspect the check's scope before the user's machine.**
- **A reproduction is a hypothesis about reality, so the first real run is its own ticket.**
  Ticket 39 verified the procedure against 46 assertions on a faithful bare-origin fixture,
  which retired the mechanics but not three things: Dependabot's actual commit shape, whether
  `gh pr view`'s `author.is_bot` behaves for a real bot PR, and whether the gate agrees on a
  genuinely re-authored Dependabot commit. All three are settled by one green run, and all
  three are the kind of failure nobody notices — so [53](issues/53-exercise-the-landing-procedure.md)
  exists rather than a closing sentence. Two of the 46 assertions failed during the exercise
  and **the fixture was wrong, not the script** (`8.13 → 9.0` filed as a minor bump), which is
  the usual ratio: a harness written from the same understanding as the code confirms the
  understanding, not the code.
- **A resting style held in place by a keyframe is a resting style in the wrong place, and
  a one-shot that replays is not a one-shot.** Ticket 47's prototype claimed in its own header
  that every animation played once and was then removed. Both halves were false, and neither is
  visible in a screenshot. Six resting styles were held by `animation-fill-mode: forwards`,
  which means those animations were still **attached** to their elements after everything
  settled — eleven of them — so "no element carries a stale animation" was untrue by
  measurement. And because `render()` replaces `innerHTML`, the one celebratory moment in the
  product **replayed on a font-scale tap**: `animationstart` fired again on a change that
  changed nothing. The fix that generalises is to put every resting state in plain CSS and
  key every one-shot to **the value it animates from**, not to the value it happens to be in.
  Third instance of one shape in this map — `docs-check`'s original `paths:` filter, requiring
  a check nobody had seen pass, the latency guard's uncalibrated threshold. Each looked
  configured. **The general test: if the only way to notice is to run the thing, it will not
  be noticed, and the claim in the comment will drift away from the code silently.**
- **A harness that lies about the thing it measures is worse than no harness, and it lies
  quietly.** The same prototype reserved a fixed `8rem` at the bottom of the page for its own
  control bar. At 200% font that bar is **872px** tall, so it lay across the phone and covered
  the primary action — which meant every large-font hit-test was failing for a reason that had
  nothing to do with the product, and a "green at 200%" run meant very little. The reserve is
  now measured from the bar. Worth pairing with the map's existing lessons about checks that
  cannot fail: **this one could pass, and it passed, while measuring a screen that was not the
  screen.**
- **A container query cannot express a display-to-type ratio, and will not tell you it
  cannot.** The Dynamic Type reflow needed "how many rem of type does this display hold", and
  was written as `@container (max-width: 20rem)`. Chromium compares the container's **pixel**
  width against a rem threshold resolved at the root, so `20rem` means 640px at 200% font and
  the query silently stopped matching at exactly the sizes it was written for — passing at
  100% and doing nothing at 200%, with no warning. It is measured on the real element now. The
  general trap: **a threshold expressed in a unit the measured thing also scales in looks
  scale-invariant and is not**, and the failure mode is a check that quietly stops checking.
- **A press is not a transition, because the pressed state inverts.** The primary action's
  pressed state swaps paper ground for ink label, so a 100ms cross-fade walks the ground toward
  paper and the label toward ink **at the same rate** — measured at **4.02:1 at +25ms and
  1.33:1 at +50ms**, below AA while the finger was down and fine at both ends. A static
  contrast audit cannot find it, because it never hovers and the failing frames exist only
  mid-gesture. Same family as the map's existing note that a pressed control must not
  cross-fade ink against ground; worth restating as the broader rule: **any state change that
  inverts must swap instantly, and any state change that needs a contrast check needs a
  harness that visits the state rather than resting in it.**
- **Reduced motion is not the same animations, faster — it is no animation at all, and that is
  only safe if nothing is resting on a keyframe.** Running the harness under
  `prefers-reduced-motion: reduce` for the first time found a class sitting on an element
  waiting on a timer for an `animationend` that was never going to fire. The one-shot classes
  are now not added in the first place when motion is reduced. Fourth variant of the map's
  standing lesson: **a check that was only ever run in the easy configuration is a check that
  has not been run** — and "the easy configuration" is whatever the reviewer happened to have.
- **A check can be correct code and the wrong check.** `apksigner verify` was not broken — it does exactly what it says. The defect was that what it says ("this APK is signed") was weaker than what the step needed ("this APK is signed with our key"), and **nothing can detect that gap by reading the step**, only by running it against an artifact signed the wrong way. This is the third instance of one shape in this map: `docs-check`'s original `paths:` filter, requiring a check nobody had seen pass, and the latency guard shipping an uncalibrated threshold. Each looked configured. The fix in all three was the same: **make the check compare against the thing it claims to test, not against its own success.** Now `git diff` of `docs/adr/0012-release-signing.md` vs `check_attribution.py`'s reasoning defect in ticket 29 — where a *correct* check carried a *wrong* rationale and was deliberately left alone — reads as a deliberate line: correctness of the code is the gate, accuracy of the comment is the ticket.
- **An empty block looks configured, so nobody notices it has no shape.** Ticket 48 asked where
  to add the device ABI and found that `docs/quality/acceptance-gate.md`'s Gate Status block
  was `"classes": {}` with **no populated entry specified in any document** — a block written
  empty by ticket 28 and never revisited, so the schema ticket 36 would have *invented while
  writing the checker that enforces it*. The reusable move: **when adding a field to a
  machine-read structure, check that the structure has a shape first**, because an empty
  object needs no shape and therefore never fails. It is the same family as a gate that was
  never exercised — the absence of a defect reads exactly like the presence of a design — and
  the fix is the same: `gate_version` **1 → 2**, a specified shape, and a checker that reads
  the version and **refuses one it does not know** rather than guessing.
- **A claim restated by hand in N places is a claim that will be right in some of them.** The
  gate's scenario count at charting was fifteen, stated in six live places. Ticket 44's fourteen → fifteen
  landed in three of them, and **`GLOSSARY.md` was left saying "Fourteen scenarios per device
  class"** while ADR-0008's Consequences still said the gate grew "to fourteen … thirty runs
  became forty-two". Both were correct when written, both are live documents making a false
  statement about the product, and **neither looked wrong** — a document saying fourteen is
  indistinguishable from one saying fifteen unless something compares them. Fifth instance of
  this map's standing lesson, after `docs-check`'s original `paths:` filter, requiring a check
  nobody had seen pass, the latency guard's uncalibrated threshold, and ticket 44's own
  half-landed count bump. Whether to derive it, check it, or state the relationship instead
  of the numeral is [57](issues/57-should-the-scenario-count-be-checked.md).
- **"Log it" and "enforce it" are not the only two answers, and the third is common.** Ticket
  48 offered *rejected* and *merely recorded* for a run on an ABI OpenFlow does not ship, and
  both are wrong: failing a scenario for the phone's architecture is the same error as failing
  it for transcription accuracy, and merely recording it makes absence of evidence look like
  evidence. The answer needed a third verb — **the run is excluded from coverage without being
  judged** — and the protocol had no word for it until this ticket added one. Worth reaching
  for whenever a rule offers two options: ask whether the case is actually *not counted*,
  which is neither logged nor scored. The same third category turns up whenever a measurement
  is real but meaningless (a benchmark row on hardware nobody will ship to), which is why
  "record it" and "reject it" both feel exhaustive and neither is.
- **The thing with no real hardware behind it is the thing most likely to be faked, and it is
  usually faked by something wearing its clothes.** ADR-0010 retains `x86_64` for exactly one
  reason: `android-test.yml` runs the instrumented suite on an **`x86_64` emulator** — and
  that workflow uses the **`pixel_6` profile**, so the one shipped ABI with no device behind it
  is presented as the device class a reader would most like the coverage gap closed with. The
  retention reason and the coverage gap occupy the same square, which is why
  "an emulator run is not a Device Class run" had to be written into the protocol rather than
  left as an understanding. Generalisable: **when an exception exists to serve a tool, check
  what the tool looks like** — it is usually shaped like the thing the exception is not.
- **An amendment that adds a second copy of a machine-read format creates the ambiguity it
  has to name.** Specifying the block's shape meant a second `json` fence in the same section,
  and a checker that reads the wrong one reports on placeholder values and passes. The rule —
  the record is the first fence after the heading, not the last — is now stated in the protocol
  and handed to ticket 36, rather than left for whoever writes the parser to discover. The
  general rule: **adding a worked example next to a live instance of a machine-read format is
  a change to that format's contract**, and the contract has to say which one is which.
- **Two rules that each sound right can contradict each other in the case neither was written
  for.** Ticket 65 settled "nearest scope wins" and "longest match at a position wins" in
  different rounds, and they disagree for an app-scoped `sign` against a global `sign off` —
  neither rule's author had that case in view, which is why it survived three agreed rounds.
  The fix was not to pick one but to find the ordering that keeps both promises (specificity
  filters, then the scan). **When two rules are agreed independently, check them against a
  case neither was written for** — separately-stated rules are not separately true.
- **A value asked to carry two questions is a lie about what it controls.** The same ticket
  found origin being asked to answer "may stage 8 write here?" and "may stage 7 rescan here?"
  at once, which one two-value enum cannot hold — and the tempting fix, a per-stage flag on
  each segment, moves the ambiguity rather than removing it. Making origin mean stage 8's
  authority *only*, with stage 7's rule stated separately in the shape ticket 60 had already
  used, left no gap. Same family as `RouterContext` gaining an app field nothing reads
  (ticket 52): a field that lies is worse than a missing one, because a missing one gets asked about.
- **A verdict about two different facts has to be two marks, and the schema will not stop
  you collapsing them.** Ticket 66 asked how History shows a recoverable entry and found the
  storage underneath was already lossy: ADR-0002 gives a Dictation one terminal outcome and
  ticket 14 stores it in one `outcome` column, but "did the text land" and "did the cleanup
  run" are independent — an entry can be unprocessed *and* not inserted, and an unprocessed
  one can have landed perfectly well, which is the case most likely to be mislabelled
  **inserted** and therefore most likely to fail a reader. The prototype shows two marks
  with one limit each. **The general form: when a single stored value is asked to answer a
  question about a conjunction, every rendering of it is a guess, and the guesses disagree
  in whichever direction is least visible.** Same family as the latency guard declining to add
  a fourth health value (ticket 31: one job, two mechanisms), which is why this one did not
  add a `refine_failed` outcome either — it needed a second fact *beside* the outcome, not a
  fifth value inside it.
- **The eighth instance of a check that could not fail, and the first one written to be
  correct.** The prototype's honesty audit compared `limitsFor()` against `LIMITS.place` —
  and `limitsFor()` *reads* `LIMITS.place*, so it agreed with itself by construction and
  reported "Consistent" after the limit sentence was stripped off a Place text button
  entirely. Every other instance in this map was a check that was never exercised; this one
  was exercised, passed, and was measuring itself. It now reads the rendered DOM, and each of
  its six rules was confirmed to fire against deliberate damage. **The general test is now
  the map's standing one plus a second half: break the thing on purpose, because a checker
  that has never seen a failure has not been shown it can fail.**
- **A checker fixed three times is the one that has stopped being trustworthy.** The contrast
  auditor reported 214 of 620 roles failing at 1.06:1 — ticket 37's black-on-black figure,
  arriving from the wrong direction. Its colour parser did `.slice(0,3)` on
  `rgba(0,0,0,0)`, so every transparent ancestor read as **opaque black** and the ground
  walk stopped on the first one it met. It took three fixes to notice that the number was
  wrong rather than the page, and the tell was that the figure was *familiar* — a ratio this
  map had already recorded as a real bug elsewhere is not evidence of a real bug here. **A
  surprising number deserves the same suspicion as a comfortable one**, and a checker that has
  been repaired repeatedly should be required to fail on demand before it is believed again.
- **Two facts about one row must be visible in words, because the styling cannot be trusted
  with the distinction.** The ticket's prohibition — do not imply text has been inserted when
  it is still recoverable — survives a monochrome rendering only if the words say it. Every
  row therefore names where its text is (`In Mail · Message body`, `Not in any field · 2
  attempts, last 25 min ago, cancelled`) rather than relying on a chip's colour, and every
  affordance that could be misread carries its own limit beside it. **An affordance's
  absence needs a sentence too**: an inserted entry must say *why* it offers no Place text, or
  its absence reads as an oversight rather than a decision.

- [How does History present recoverable and unprocessed entries?](issues/66-history-recovery-surface.md): **prototype built and verified; awaiting an owner verdict on which variant wins** (A ledger recommended). - [How do dictionary and snippet entries match spoken text?](issues/65-dictionary-snippet-matching.md): **one matcher for both entry kinds, and the prototype's disclosed rule is rejected outright** — its branch on whether a trigger contains a space was the defect, which is why `sign off` fired inside "design off" while `sig` was safe inside `signal`. A trigger is a **token sequence**: a token is a maximal run of Unicode letters and digits with an apostrophe between letters internal, compared case-folded and **without** accent folding (`cafe` ≠ `café`, because folding would make `resume` match `résumé`), so punctuation and case in a stored trigger are not load-bearing. One match replaces **first matched token's start to last token's end**, and matching is re-tokenized at stages 6/7 so it **does not depend on stage 1's normalization**. **Specificity filters per position before the longest-match scan**, which is the one rule that had to be added mid-grill: nearest-scope-wins and longest-match-wins contradict each other for an app-scoped `sign` against a global `sign off`, and filtering per position keeps both promises — the app's entry wins even against a longer global one — while leaving the scan order-free, so **entry-list order is never consulted**. Duplicates are compared as token sequences and **rejected at save**, naming the existing entry (the only option where the user learns); cross-kind overlap is allowed and settled by stage order. **Origin is two values and means stage 8's write authority only** — stage 7's own insertions are never rescanned by stage 7 while a stage-6 body is, and a match spanning a stage-6 boundary is wholly authored; **a dictionary body is authored too**, so stage 8 cannot repair its capitalisation. Accepted rather than engineered away: a snippet body is never dictionary-corrected, and **triggers are unusable in a script without word spacing** (a CJK run is one token) — stated so it cannot read as support. Contract in `docs/architecture/refiner.md`'s new "Entry matching" section; glossary gains Dictionary Entry and Origin Segment; the prototype's false disclosure replaced by the rule under the trigger field; **`G3` widens to "a dictionary entry or snippet" with no new scenario ID, so the count does not move**. **Graduated:** [68](issues/68-implement-the-transcript-refiner.md) — the refiner is four settled contracts and zero lines of production Kotlin, and no ticket owned it.

- [How do the three behavioral answers select a Device Class?](issues/64-device-class-assignment.md): the class is **derived from a recorded Hostility Profile, not assigned beside it** — three probes (survive 10 min backgrounded screen-off; overlay permission survives a reboot; a backgrounded dictation returns no usable transcript) are each one observable event rather than a judgement about an OEM, and the class follows from the **count** of hostile answers (`0`/`1`/`2–3` → the three tiers), so the class key is **recomputable** and two independent testers agree without conferring. Comparability across testers is the property that makes crowdsourcing the sanctioned route out of `N/3`, which is why a published function beat an owner's label. Axis 3 **cannot be read from settings** — discovered by running, as ticket 59 settled for insets — which is why all three became probes; the 10-minute interval is a **labelled provisional threshold**, the latency guard's precedent. **Any `unknown` means no class at all**: excluded from coverage and reported unresolved, never defaulted either way, because non-hostile credits an unmeasured device and hostile narrows the gate silently — ticket 48's third verb again. The profile describes **a device in a configuration, not a bare model**, so the four settings that can move an answer are recorded and re-probing is required after any of them or an Android major change, **with a changed class invalidating that device's earlier cells**; there is deliberately no defaults-only purity rule, which would exclude the handsets most likely to volunteer. **Rejected:** an owner-assigned label (unfalsifiable prose), worst-axis (one flaky probe reassigns wholesale), reference-profile matching (needs hardware the project lacks, plus a metric inside the metric). **The ticket's two former examples contradicted each other and the rule above them** — one decided by brand, one by behaviour — and are gone; the class keys keep their asymmetric spellings because the destination and the JSON contract name them, so **the suffix carries no meaning** and the glossary says so. `gate_version` **5 → 6** adds `hostility` and `config` to the class entry, and costs nothing because `classes` is empty.
